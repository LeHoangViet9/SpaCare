# Synthetic Preview seed (offline implementation)

This script is manual only. It is not called by build, deployment, server startup or login.
No Atlas connection or seed write was performed during implementation.

## Safety and prerequisites

- Run locally from the repository, never on Vercel. Any nonempty VERCEL* variable blocks execution.
- Use only a private env file outside the repository. `.env.local` and `.env.live.local` are rejected and never loaded. The file must be a regular file; repository paths and symlink files are rejected.
- Require NODE_ENV=test, SPACARE_ENV=test, SPACARE_TARGET_DATABASE=spacare_test. Only an Atlas SRV URI with explicit /spacare_test is accepted; database query overrides are rejected by the existing guard. authSource may only be admin or spacare_test.
- Supply the independently verified Atlas Staging SRV hostname via --allow-host. Matching is exact (case insensitive), no wildcards or suffix matching. Do not obtain the expected hostname from the URI being checked. The guard cannot determine the organizational ownership of a hostname; verify it in SpaCare-Staging and use a database user limited to readWrite on spacare_test.
- OWNER must already exist, be active, and match PREVIEW_OWNER_ID. The script derives spaId from this OWNER; it never creates or updates OWNER or Spa.
- Initial run requires a dedicated empty business namespace for this spa (setup OWNER/Control may exist). Existing customers/catalog/financial records, day books or other users cause a stop. Other spa namespaces are untouched.
- setup.ts must already have created collections/indexes. Transactions require a replica set or sharded deployment. Actual permissions, topology and indexes remain unverified until separately approved Staging execution.
- Before writing, ensure every Preview/worker sharing Staging is running the server-side push guard described in PUSH_SAFETY.md, or keep push disabled in older runtimes. Normal operations queue synthetic invoice notifications tagged QUARANTINED; the seed never calls the sender. An old deployment ignores this new field and must not dispatch the backlog.

## Private configuration

Use a new external file such as $HOME\.spacare\preview-seed.env. Do not overwrite either application env file or the existing owner config. Populate privately:

- NODE_ENV=test
- SPACARE_ENV=test
- SPACARE_TARGET_DATABASE=spacare_test
- MONGODB_URI: Staging credentials, explicit spacare_test path (never paste in logs/chat).
- PREVIEW_OWNER_ID: existing Preview OWNER ObjectId, obtained from the Staging UI.
- PREVIEW_STAFF_PASSWORD: a separate test-only password, 12–128 characters; never printed.

An existing preview-owner.env can also be used after adding the two PREVIEW_* keys privately; SEED_OWNER_* keys are tolerated but never used. Unknown keys are rejected. File values take priority over inherited database/password variables within the child process only. Cloud identity is checked before loading the file and cannot be cleared through it.

## PowerShell (not executed during implementation)

```powershell
$PreviewSeedEnv = Join-Path $HOME '.spacare\preview-seed.env'
$StagingHost = 'REPLACE_WITH_VERIFIED_STAGING_SRV_HOST'
npm run db:preview:check -- --env-file "$PreviewSeedEnv" --allow-host "$StagingHost"
```

CHECK validates configuration, exact host, reference dependencies and actual operation input schemas; it does not connect, query or write any database. PASS is not a connectivity, permission or transaction test.

Only after separate approval, on your machine:

```powershell
npm run db:preview:seed -- --env-file "$PreviewSeedEnv" --allow-host "$StagingHost" --confirm WRITE-SYNTHETIC-spacare_test
```

This second command connects and writes. No --force, reset or automatic retry outside domain transaction retries is provided.

## Planned dataset

| Group | Count / coverage |
| --- | --- |
| Customers | 20; 4 untouched new customers, fictional names and non-routable 000-prefixed phones |
| Staff | 5 STAFF, first cashier; no MANAGER role exists in current schema |
| Service groups / services | 6 / 20; fixed service commissions |
| Package templates | 10; session packages and 36-month TIME packages |
| Treatments | 12 purchased + 1 one-use gift generated by sellPackage = 13 |
| Treatment uses | 10: three of ten, five of five, and a shared two-treatment mixed visit |
| Appointments | 25 at 10:00 Vietnam time on separate future dates; 23 confirmed, 1 cancelled, 1 postponed; multi-service/multi-treatment/mixed selections |
| Invoices | 30: 12 package + 1 gift + 8 session + 1 mixed + 8 service |
| Products / movements | 10 / 11: 10 manual movements plus 1 sale movement; empty, low and sufficient stock |
| Cash cards | 5: 4 purchased + 1 gifted; full, partially redeemed and exhausted balances |
| Deposits | 5; one allocation to a partially paid package invoice |
| Attendance / leave / payroll | 15 workdays, 5 reviewed leave records (permitted/unpermitted), 5 draft payrolls with DAILY salary policy, bonus and deduction |

Cash and bank transfer only. Package commission uses the existing 5% cumulative rounding and equal two-person split. Service commissions use configured fixed amounts. No fabricated signatures; treatment use is recorded through the supported STAFF_RECORDED path.

Customer email is not a schema field and is intentionally omitted. Completed appointments are intentionally omitted: appointment creation forbids the past and completion forbids future visits. Complete a confirmed visit manually after its arrival time; no direct state injection or validation bypass is used. There is no actual rescheduled replacement here: postponed is a supported status. Payroll remains draft and no payroll payment is fabricated. No customer login accounts are created.

Dates are anchored to the first run in Asia/Ho_Chi_Minh. Attendance days can cross the previous month; the current-month draft only includes days in that month.

## Transaction, replay and reconciliation

Every business write uses operate(): current DB permissions, per-spa Control serialization, transaction, schema checks, immutable operation fingerprint and idempotency records remain active. Existing Control revision/invoice counters advance through normal domain operations; OWNER credentials/profile stay unchanged. Only seed manifest/completion markers are written directly to Idempotency, inside transactions. No direct financial inserts, deleteMany, dropDatabase, schema migration or index reset.

Marker/key prefix: spacare-synthetic-preview-v1. Fixture references are resolved from operation results, never guessed collection fields. Manifest records the day and plan fingerprint. An incomplete replay with a changed staff password is blocked by operation fingerprints. A completed replay never rotates staff passwords. Concurrent operation retries use the same keys and existing unique indexes. Completed reruns skip all operations, then reconcile; they do not reset manual edits. An incomplete batch can resume only on the same Vietnam day. Cross-day partial batches stop for review; do not delete the marker to restart.

The batch is **not one global transaction**: completed steps remain if a later step fails. Individual financial operations are atomic. Review and rerun with unchanged configuration on the same day. An offline mock replay test is not proof of real MongoDB index/concurrency behavior.

After writing, a transaction snapshot checks invoice payments/allocations/card redemption and statuses, service/product totals, package 5% commission ledger, card/deposit origins and balances, stock movement arithmetic, customer/treatment/appointment references, treatment quotas, cash receipt sources, payroll arithmetic and unchanged OWNER snapshot. Any mismatch stops without repair. Reconciliation intentionally supports this seed's unreversed histories; later cancellation/refund/manual workflows may require separate reconciliation before rerunning.

## Validation boundary

Offline tests exercise fail-closed configuration, confirmation, real domain input schemas, reference resolution, unchanged OWNER and adversarial reconciliation fixtures. A full-plan test invokes the real operate() services and real Mongoose document validation with entirely in-memory persistence: exact counts, financial reconciliation, interrupted package/gift rollback and duplicate-free replay are checked. mongoose.connect is replaced with an unconditional failure. They do not verify Atlas topology, network allowlists, live indexes, real MongoDB transaction rollback or full end-to-end authorization. Those require a separately approved Staging test. No Production access is needed or permitted.
